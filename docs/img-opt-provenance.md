# Gallery webp (public/img-opt) — provenance

Prebuilt, committed assets. They are NOT regenerated by the build, and the generator is deliberately not in this repo (no new dependency, no script that imports an undeclared package). The generator, corrected regen-check script, and QA evidence (hash-manifested) are archived outside the repo at `D:/Codex/vinyl-external-evidence-20261002/image-delivery-review-1735/` (see its README.md); `_evidence/` is gitignored and not tracked.

## Naming / caching
Each filename carries the first 12 hex of the **SHA-256 of the encoded webp bytes** (not of the source). A different quality, effort or encoder version therefore yields a different name. No `/img-opt/*` immutable cache rule exists in `public/_headers`; the files are served with the default asset headers. Add one only after deciding that is wanted.

## Recipe (one-off, run outside the build)
- Tool: sharp 0.34.5 (Apache-2.0; prebuilt binary @img/sharp-win32-x64 is Apache-2.0 AND LGPL-3.0-or-later), libvips 8.17.3, libwebp 1.6.0. sharp is a transitive dependency (astro@5.18.2, wrangler>miniflare), pinned by package-lock.json; it is not a declared dependency of this package.
- Source: `public/wp-content/uploads/<key>-768x432.jpg` (the WordPress-generated 768x432 renditions, copied unchanged).
- `sharp(src).resize(W, round(W*432/768), {kernel:'lanczos3'}).webp({quality:82, effort:6}).toBuffer()` for W in 384, 768.
- Verified 2026-10-07: re-encoding all 16 outputs with the versions above reproduced the committed bytes exactly (16/16 identical). Other platforms' libvips builds may differ byte-wise.
- `src/data/img-opt.json` maps source path to the two output paths (plus psnr / byte counts recorded at generation time).

## Rendering
Measured with getBoundingClientRect: figure and img are 370 CSS px wide at 390 viewport, 362.6 at 1440, 220-304.5 at 768-1024; height keeps 16:9; object-fit is the default fill (no cover or square crop). The 768w variant is the full source width and is never upscaled at encoding time. Display is a separate matter: at a 390 px viewport and DPR3 the 370 CSS px image needs ~1110 device px, so the browser stretches the 768 px file (a limit of the 768x432 source); at 1440 px DPR2 (~725 px needed) it is not stretched; 384w is only chosen where it is at least the rendered width at DPR1.
